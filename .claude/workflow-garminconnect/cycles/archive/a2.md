# Adversarial Cycle A2 — Design Pre-Mortem

**Subject:** `design.md` (Phase 1 — Activity Download), in light of `decisions.md` (DEC-001 through DEC-011, all accepted) and `prd.md` open assumptions A/B/C.
**Run:** 2026-05-17.
**Iteration:** 1.

The exercise: imagine it is **November 2026 — six months after Phase 1 shipped.** The integration is in a state we'd describe to other devs as "failed." Write the post-mortem *now*, while changes are cheap.

---

## A2.1 — Three failure narratives

### Narrative 1 — Technical: "the silent sidecar"

> *October 2026.* A beta user with 12 years of Garmin history did the maximum 5-year backfill. Their `imported.json` grew to roughly 38,000 entries (~22 MB). Every incremental sync now reads + parses + atomically rewrites the whole file. On their HDD-based desktop, each sync takes 12–18 seconds before any network call happens — well past REQ-NF-Perf-003's 5s budget. Worse: the atomic-write helper holds the GIL during `json.dumps`, so the worker thread blocks for ~600ms per sync, intermittently breaching REQ-NF-Threads-001 (the 100ms event-loop budget) on slower machines. Bug reports come in as "sync is slow" with no obvious cause; we don't have a metric in the observability plan that flags sidecar size. By the time we ship a sqlite-backed sidecar in Phase 1.5, several users have abandoned the integration.

**Root:** DES-002 chose JSON for the sidecar map. DES-008 has no observability for sidecar I/O time.

### Narrative 2 — Technical: "the platform that wasn't"

> *September 2026.* Apple ships macOS 26 with TLS-stack changes that subtly affect `curl_cffi`'s browser-impersonation behaviour. Garmin's WAF starts rejecting the impersonated handshake. macOS users see `GarminConnectConnectionError` on every connect attempt; Windows and Linux are unaffected. Our `curl_cffi` is pinned to a specific version in the bundle. The fix lives upstream and takes ~6 weeks. We have no fallback transport — we can't swap to `requests` because Garmin's WAF flags un-impersonated clients. macOS users are stuck. The forum fills with "is GC abandoned?"

**Root:** PRD open assumption A/B both predicted this class of risk. DES-001/DES-005 have a single transport path with no degradation strategy.

### Narrative 3 — Organizational: "the unmaintained dep"

> *Sometime in late 2026.* The maintainer of `python-garminconnect` has health issues and stops shipping. Two months pass without a release. Garmin then pushes a small SSO change that breaks `Garmin.login()` (this happens every 6–12 months historically). A community fork emerges (`garminconnect-community`) but it has a different API surface — and our DES-005 decorator and DES-008 error switch table are wired directly to `garminconnect`'s class names and method signatures. Swapping is a multi-day refactor across both Python and C++. We delay; users get more frustrated; some migrate back to Strava + USB. Once we do the swap, we discover our tests asserted concrete exception types, so the test suite breaks too.

**Root:** No abstraction seam between our code and `python-garminconnect`'s public API. This is the textbook A2.4 migration-trap finding.

### Narrative 4 — Security: "the silent permission widening"

> *June 2026.* A user runs a third-party backup tool that mirrors their home directory to network storage. The tool, for compatibility with the mirror, sets files to mode `0644` in the local copy *and the original* (it has bugs). Next GC launch: `tokens.json` mode is `0644`. Per REQ-006, GC refuses to load and forces re-login. Good outcome. **But:** the error surfaced to the user is the generic "Couldn't reach Garmin Connect" string from DES-008's fallback (because we didn't add a specific error code for "token-file-permissions-widened"). The user has no idea *why* re-login is needed. They re-enter their password, GC writes the token at `0600`, the backup tool widens it again the next day. Cycle repeats. After the third cycle the user gives up and disables the integration. We get a bug report titled "GC keeps asking me to re-login every day"; it takes us a month to trace.

**Root:** DES-008's error map has no entry for "token rejected due to permission mismatch." Friendly translation degrades to generic, hiding the actual diagnosable cause.

### Narrative 5 — Organizational: "the orphaned reconnect"

> *August 2026.* A user buys a new Garmin watch tied to a new Garmin account (they sold the old setup). They click Disconnect: per REQ-012, `tokens.json` is deleted but `imported.json` is intentionally **preserved**. They reconnect with the new account. Garmin issues new activity IDs from a different sequence — but a few collide by chance with old IDs (Garmin activity IDs aren't globally unique across accounts; they're per-account integers). Result: a few new activities are silently *skipped* by the Tier-1 sidecar dedup (DES-010) because their `garmin_activity_id` happens to match an old entry. The Tier-2 RideCache check would catch most because the new activity's `startTimeGMT` differs from the local-filename of the recorded skip — but the sidecar short-circuits *before* Tier-2 runs.

**Root:** DES-010's two-tier dedup short-circuits on Tier 1 (sidecar) without considering that sidecar entries from a *previous* Garmin account are now stale. DEC-003's choice to preserve `imported.json` across Disconnect (REQ-012) didn't account for account-change semantics.

## A2.2 — Chaos questions

### Primary store unavailable for 30 minutes
"Primary store" interpretations:
- **Garmin Connect (cloud) down:** Every sync request fails fast (`GarminConnectConnectionError`). DES-005 retries 3× with backoff, then surfaces via ErrorBus. No data loss. Recovers on next sync trigger. **OK by design.**
- **Local filesystem (athlete-config-dir) unavailable** (e.g., athlete dir on a network mount that drops): Token read fails → forced re-login flow. Sidecar write fails → ErrorBus error + sync aborts. No corruption (atomic-writer). **OK by design.**
- **Embedded Python sub-interpreter wedged** (PythonEmbed bug): `capabilities()` returns 0; user sees tile go non-functional. **There is no automatic restart of the sub-interpreter in DES-001.** Recovery requires a full GC restart. **Finding A2-001.**

### Network partition between components
Single-process; the only meaningful boundary is GC ↔ Garmin. Covered above. The C++ ↔ Python boundary is in-process; "partition" there means the worker thread is alive but the sub-interpreter is wedged — same as the third bullet above.

### 10× current traffic
"Current traffic" for this feature = "activities per user per sync." 10× = 30 activities per incremental sync instead of ~3. At 1 req/sec that's ~30 seconds — slow but works. 100× = 300 activities = 5 minutes; uncomfortable, but only happens on first-connect backfill, where progress is visible. **Real "10×" scaling concern is the sidecar growth from Narrative 1, not request rate.**

### Major dependency yanked from registry / breaking change pushed
- **`python-garminconnect` yanked from PyPI:** Live installs (which bundle a pinned wheel) keep working. Building from source breaks until we vendor or fork. → already covered as Narrative 3.
- **`python-garminconnect` ships breaking 2.0:** We pin to 1.x; no automatic upgrade. → safe by pin.
- **`curl_cffi` ships breaking change:** Same — we pin. → safe.
- **Garmin pushes SSO change:** This is the *interesting* one. We can't pin against a remote service. Library upstream fixes; we re-bundle. Time to fix = library response time + our release cadence. **Finding A2-002.**

### The user takes a 3-week vacation
Does the system keep running unattended? **Yes** — there is no scheduled background sync triggered by Phase 1; sync is user-initiated or scheduled by GC's existing CloudService auto-sync (which the user opts into). If Garmin tokens expire during the 3 weeks (the library's refresh-token TTL is ~30 days, but Garmin sometimes invalidates earlier on suspicious behavior or password change), the user returns to a forced re-login. **Acceptable — and already covered by REQ-NF-Compat-001.**

## A2.3 — Cost worst-case

No monetary cost: no SaaS billing, no metered API. Resource costs:

| Resource | Steady state | 10× user | 100× user | Cliff |
|----------|--------------|----------|-----------|-------|
| Disk — sidecar | ~10 KB per 100 imports | ~6 MB at 60K imports | ~60 MB at 600K imports (implausible) | **~10–20 MB**: JSON parse becomes user-visible slow (Narrative 1). |
| Disk — staged FIT files | ~50 KB × N during backfill, then cleaned up by GC's existing import path | proportional | proportional | None — bounded by GC's existing staging policy. |
| RAM — embedded Python | ~30–80 MB constant | unchanged | unchanged | None at this scale. |
| Network bandwidth | ~50 KB per activity downloaded; 1 req/s ceiling | unchanged ceiling | unchanged ceiling | None — capped by REQ-NF-Perf-002. |
| **Garmin "cost" (ToS risk)** | Within 1 req/s envelope: no observed impact | If a future bug spikes rate | Temporary account restriction (free to recover, but very high user cost) | **The cliff is "any sustained breach of 1 req/s."** This is the most expensive cost cliff in the system, and it's measured in user trust, not dollars. |

**The interesting cliff is the sidecar one** (Narrative 1). It's not a hard wall — it's a soft degradation that hits real users with long histories. **Finding A2-003.**

## A2.4 — Migration trap

**Least-trusted component: `python-garminconnect` itself.**

Why it's the most likely thing to need swapping:
- Unofficial wrapper around a private Garmin API.
- Maintained by a small team; the upstream readme explicitly says "may break at any time."
- Has competitors with overlapping but non-identical surfaces (`garth`, `garminconnect-community` if it materializes, or even a future official Garmin SDK).
- Historical pattern: similar wrappers in other ecosystems (Strava community libraries, Withings community libraries) have churned every 1–3 years.

What currently makes swapping expensive (per the design as drafted):
1. **DES-005** decorates concrete `gc.Garmin.login`, `gc.Garmin.get_activities`, `gc.Garmin.download_activity`, `gc.Garmin.get_user_profile` — method names + signatures bound at import time.
2. **DES-008** error switch table is keyed on the library's concrete exception class names (`GarminConnectAuthenticationError`, `GarminConnectTooManyRequestsError`, etc.).
3. **DES-002** stores tokens in the library's native `tokens.json` format (the library reads/writes it).
4. **DES-001** worker code constructs `Garmin(email, password, tokenstore=path)` — that constructor signature is the library's.
5. **Phase 2 TDD tests** (not yet written) will inevitably assert against these names.

Cost of swap as drafted: roughly **5 files touched in Python + 1 file touched in C++ + test churn**. Hours of work + careful re-test, plus exception-class re-mapping that's easy to get subtly wrong.

**Seam to build *now*:** a thin Python adapter that wraps `garminconnect.Garmin` and exposes a GC-stable interface. DES-005 decorator and DES-001 worker call the adapter; nothing else touches the underlying library directly. Swap becomes a one-file change to the adapter.

This is cheap to build now (one small Python module + tests) and approximately impossible to retrofit cleanly once Phase 2 tests are wired against concrete names. **Finding A2-004 — recommended fix-now.**

## Findings

### Finding A2-001 — No recovery path for wedged embedded-Python sub-interpreter
- **Severity:** non-blocking
- **Description:** If the PythonEmbed sub-interpreter wedges (deadlock, native crash inside Python, GIL stuck), DES-001's worker has no logic to detect, kill, and re-create it. Recovery requires a full GC restart.
- **Affects:** DES-001, REQ-NF-Reliab-001.
- **Disposition:** defer-with-ticket — Phase 1.5 follow-up. Document explicitly in the DES-001 "Failure modes" subsection so it's not a silent gap.
- **Rationale for not fix-now:** Detecting "wedged" reliably (vs. "slow") is non-trivial; the only signal is a thread heartbeat with a timeout. Phase 1 ships behind a default-OFF flag with beta users who can restart; the cost of getting the heartbeat wrong (false-positive kill of a slow-but-fine call) is worse than the cost of asking beta users to restart. Revisit after beta data.

### Finding A2-002 — No bound on library-response-time when Garmin changes SSO
- **Severity:** non-blocking (informational with documentation duty)
- **Description:** When Garmin pushes an SSO change, the time-to-recovery is roughly `library-upstream-fix-time + our-release-cadence`. We cannot bound the first term; the second is bounded by our own ship discipline.
- **Affects:** project risk register (not a code finding).
- **Disposition:** accept-with-rationale — document in PRD's Known Limitations (REQ-NF-Compat-001 already calls out related ToS risk; extend its body to include "Phase 1 depends on a third-party library to track Garmin's SSO changes; outages of hours-to-weeks are possible during transitions"). **Action:** PRD edit.

### Finding A2-003 — Sidecar JSON degrades on long-history users
- **Severity:** non-blocking (becomes blocking if real beta users hit it)
- **Description:** Narrative 1's "silent sidecar." For users with >~10K imported activities, sync-time degrades and may breach REQ-NF-Perf-003. There is no metric in DES-008's observability plan that surfaces sidecar I/O time.
- **Affects:** DES-002, DES-008, possibly REQ-NF-Perf-003.
- **Disposition:**
  - **Fix-now (cheap):** add an observability signal to DES-008 for sidecar-read-time + sidecar-size, so we *detect* the cliff in beta instead of hearing it via bug report.
  - **Defer-with-ticket:** sqlite-backed sidecar is a Phase 1.5 follow-up; do not build it in Phase 1 (premature scaling).

### Finding A2-004 — Migration trap: no seam between our code and `python-garminconnect`
- **Severity:** blocking (cheap now, expensive later)
- **Description:** Per A2.4 analysis. Without a thin adapter, swapping the underlying library is a multi-file refactor across Python + C++ + tests. With one, it's a one-file change.
- **Affects:** DES-001, DES-005, DES-008. *Does not* require re-opening DEC-002 (the worker design stands); the adapter is a pure design-layer addition.
- **Disposition:** fix-now — introduce **DES-012 — `garmin_client.py` adapter** and route DES-005 / DES-001 / DES-008 through it.

### Finding A2-005 — Token-permission rejection has no specific user-facing message
- **Severity:** blocking (user-trust failure mode from Narrative 4)
- **Description:** DES-008's error map has no entry for "token-file-permissions-widened." Users get the generic "Connection failed" and enter a loop (re-login, backup tool widens again, re-login, …) with no diagnostic information.
- **Affects:** DES-002 (the rejection path), DES-008 (the error map).
- **Disposition:** fix-now — add a `TokenPermissionsRejected` error class produced by DES-002 on permission mismatch; add a specific entry to DES-008's switch table with text that *names the file path* and *names the expected mode* so the user knows what to fix.

### Finding A2-006 — Cross-account reconnect can silently skip new activities
- **Severity:** blocking (data-integrity failure mode from Narrative 5)
- **Description:** Per REQ-012, `imported.json` is preserved across Disconnect. If the user reconnects with a *different* Garmin account, the sidecar's `garmin_activity_id` keys are stale (they belong to a different account's ID namespace) and can collide with the new account's IDs. DES-010's Tier-1 dedup short-circuits before RideCache (Tier-2) can catch the mismatch.
- **Affects:** DES-002 (sidecar schema), DES-010 (dedup logic), REQ-012 (preservation semantics), REQ-008 (dedup acceptance).
- **Disposition:** fix-now — extend the sidecar schema to include the **Garmin user ID** (or `displayName`) as a per-entry tag (already available from the SSO response). On Tier-1 lookup, if the entry's user-ID doesn't match the currently-connected account, treat it as a miss (proceed to download). Cost: small schema change + a migration for any pre-fix sidecar (interpret missing user-ID as "matches" — preserves Phase 1 behaviour for single-account users).

### Finding A2-007 — Backfill cancellation responsiveness during long parse
- **Severity:** non-blocking
- **Description:** Cancellation flag is checked at DES-005 sleep release + DES-009 loop head. If `FitRideFile` parse of an unusually large FIT file (e.g., a 24h ultra) takes 10+ seconds, cancellation is ignored for that duration.
- **Affects:** DES-009, REQ-NF-Cancel-001.
- **Disposition:** accept-with-rationale — `FitRideFile` parse is not under our control here, and adding cancellation hooks inside it is out of scope for this feature. Worst case is a 10-second delay on cancel, which is acceptable. Document in DES-009.

### Finding A2-008 — Wizard window-chrome / phishing distinctiveness
- **Severity:** informational
- **Description:** A fake Qt-styled credentials dialog spoofing GoldenCheetah could trick users into entering Garmin credentials. The wizard does not currently call out any anti-phishing distinguishers (window title, GC logo placement, account avatar).
- **Affects:** DES-003.
- **Disposition:** accept-with-rationale — same exposure as every other CloudService in GC; not a regression. Phase 1 is not the place to invent a new anti-phishing pattern. Re-visit if Strava/Dropbox flows get hardened in GC core.
