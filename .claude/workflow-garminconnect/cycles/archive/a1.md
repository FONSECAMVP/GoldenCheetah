## Hat 2 — Persona

### (a) Novice
- **F-N1 — Garmin login error wording.** Garmin's SSO returns codes like `InvalidCredentials`, `MfaRequired`, `AccountLocked`, `CaptchaRequired`. Library bubbles them up. Novice user will see "InvalidCredentials" and not know it means wrong password. → **Add REQ for friendly error translation** (Phase 1).
- **F-N2 — Captcha trap.** Garmin sometimes serves a CAPTCHA on suspicious login. Library does not solve it. Novice will be stuck with no path forward. → AC for REQ-002 must include a "CAPTCHA detected" code path with instructions to log in to Garmin web first.
- **F-N3 — "ToS risk notice" overwhelms novice.** If we list every risk the user will close the app. The notice should be informative without being alarming. → Add wording guidelines to DEC-004 (MFA/ToS UX).

### (b) Power user
- **F-P1 — Multi-device cross-import.** Power user has 1500 activities. Default backfill is 90 days. They'll want all of history. → Already covered by configurable date range, but is there a per-sync cap to prevent a 5-hour backfill? Spec says rate-limit only; for 1500 activities at 1 req/sec that's ~25 minutes — actually OK but document.
- **F-P2 — Custom auto-import folders.** GC supports a watched-folder auto-import. Power user might want Garmin activities to land in a specific folder, not the default. → Phase 1 nice-to-have or Phase 2? **Disposition: defer.**
- **F-P3 — Multiple Garmin accounts per athlete.** Some athletes have a public + private Garmin account. Current design says per-athlete (1 account per athlete). → Documented limitation, not a REQ gap.

### (c) Malicious actor
- **F-M1 — Token theft via filesystem.** Tokens at 0600 protect against other OS users, but not against malware running as the same user. Garmin tokens can be replayed by an attacker to download personal data. → Mitigation options: OS keychain integration (macOS Keychain / Windows Credential Manager / libsecret). Phase-1 can ship with file-only with documented risk; **add a DEC for this** (DEC-003 candidate, "token storage").
- **F-M2 — Compromised installer or supply chain.** A malicious build of GC could exfiltrate Garmin credentials. Out of scope for this REQ set, but worth noting in design's threat model.
- **F-M3 — Replay against Garmin from another machine.** Tokens copied to another machine work until they expire. Not unique to GC — same as Strava tokens in `Cloud/Strava.cpp`. → Documented inherent risk.
- **F-M4 — Athlete-config-dir poisoning.** Another GC user on the same machine writes a fake `tokens.json` into another athlete's dir. → Mitigation: don't read tokens unless file mode is exactly 0600/owner-only. Add to REQ-006 AC.

## Hat 3 — Edge case

For each input, what happens at:

| Input | Empty | One | Max | Max+1 | Negative | Zero | Unicode | Concurrent | Net-fail mid-op | Clock skew |
|-------|-------|-----|-----|-------|----------|------|---------|------------|-----------------|------------|
| Backfill date range | start>end → error? (need AC) | one-day range | 365 days | 366 days → cap? | start in future → error? | start==end → empty result, not error | N/A | two sync invocations queue or reject second? (need AC) | partial results preserved (REQ-NF-Cancel-001) | activity timestamps wrong if user clock is off — dedup key shifts |
| MFA OTP | reject empty | length 6 digits required | 6 digits | 7 digits → reject early | "-123456" → reject | "000000" → pass to Garmin | N/A | parallel OTP attempts impossible by UI | mid-OTP HTTP fail: retry or hard-fail? | OTP has ~30s window — clock skew could fail |
| Athlete config dir | doesn't exist → create it (REQ-004 silent on this) | normal | N/A | N/A | N/A | N/A | dir with Unicode chars (Windows path edge) | two sessions sharing dir | filesystem full mid-write → torn write (A1-008) | N/A |
| Activity list | 0 new → OK | 1 | typical 5-50 | 1000+ on bulk | N/A | 0 | activity names with emoji | dedup safe | resume next sync | activity timestamp UTC vs local — confirm UTC normalization |

**Findings:**
- **A1-012 — Concurrent sync invocations.** What if the user clicks Sync twice rapidly, or auto-sync overlaps a manual one? AC must enforce serialization (reject second, or queue, or coalesce).
- **A1-013 — Backfill cap.** Default 90 days; max should be capped (e.g., 5 years) to bound run-time and ToS exposure.
- **A1-014 — Empty-state vs error.** start==end empty result is success not failure; spec should say so.
- **A1-015 — Clock-skew on dedup key.** If the user's clock skewed by 1 minute, the `startTime` portion of the dedup key flips. Use Garmin's authoritative timestamp (server) for the key, not local time.
- **A1-016 — Athlete dir doesn't exist.** REQ-004 doesn't say what happens. AC: create with `0700` if missing.
- **A1-017 — Atomic file write for tokens & in-progress staging.** Write to `*.tmp` and rename, so torn writes are impossible (folds into A1-008).
- **A1-018 — Unicode in athlete-name path.** Windows path separator + Unicode is a known footgun; existing GC code presumably handles it, but call out for design review.
