# Adversarial Cycle A0 — Should we build this?

**Subject:** Integrate `python-garminconnect` to enable bidirectional sync between GoldenCheetah and Garmin Connect.

## A0.1 Existing-tool probe

| Tool | What it does | Why insufficient *for this user* |
|------|--------------|----------------------------------|
| **Garmin Express** (Windows/macOS) | Auto-uploads FIT files from USB-tethered Garmin device to a watched folder. | Windows/macOS only — **no Linux**. Requires the device be physically tethered. Misses smart-trainer rides recorded on phone / Edge units that sync only over wifi. Misses workouts/courses/plans uploaded *to* Garmin Connect. |
| **Strava round-trip** (Garmin → Strava → GC via existing `Cloud/Strava.*`) | GC can already pull activities from Strava. | **Lossy**: Strava strips structured-workout data, lap power targets, training-effect, training-load, HRV, sleep, body-comp. Forces dependence on a second cloud account. Doesn't help users who don't use Strava. |
| **Manual FIT export from connect.garmin.com web UI** | User downloads `.fit` per activity or a 30-day bundle. | Manual. No auto-sync. No way to push workouts/schedule back. Fails the "5 activities/week × indefinitely" use case. |
| **Tapiriik / GarminDB / gcexport / garmin-connect-export** | Third-party tools that scrape Garmin Connect and emit FIT/CSV. | Same ToS risk as the in-house path, but **outside GC** — separate config, separate token store, no UI, no error surfacing. Several are abandoned. |
| **Intervals.icu / TrainingPeaks** | Both offer first-party Garmin Connect sync. | Different products. User has chosen to use GoldenCheetah — switching is not a free move (1000+ activities in GC's database, custom metrics, charts). |
| **Garmin Connect IQ Connect API** (the *official* developer API) | Per-user OAuth, requires Garmin developer-program approval. | Requires an approved Connect IQ app and per-user authorization. Process is slow, not guaranteed, and Garmin has historically declined many similar integrations. Out of reach for an OSS project. |

**Finding A0.1-001:** No existing tool covers Linux + smart-trainer/phone-recorded + structured-workout retention + bidirectional. The integration fills a real gap.

## A0.2 Non-code path

Smallest non-code: a user-side cron job that runs `garminconnect` CLI to dump FIT files into GC's auto-import folder.

- **Where it works:** Pure download case, technically literate Linux/macOS user.
- **Where it breaks:**
  - No GUI for first-time auth / MFA. Users hit the OTP prompt blind.
  - Token storage is global to the OS user — multi-athlete GC installs collide.
  - Zero error surfacing — silent sync failures invisible until the user notices an activity is missing.
  - Doesn't handle workout/schedule upload at all.
  - Windows users without WSL can't run cron.

**Finding A0.2-001:** A non-code path *exists* for the download-only 80% case but excludes the 20%+ of users on Windows-without-WSL, and offers no UX for MFA or multi-athlete. The bidirectional-sync scope rules it out entirely.

## A0.3 80/20 slice

**80% slice = activity download only, no upload, no schedule push.**

- Covers the dominant user journey: "I rode my bike, I want it in GC."
- Skips: workout upload, schedule push, gear sync, structured-workout writes — all of which are write-side operations that carry the highest ToS-violation risk (Garmin's enforcement, when it has happened, has been triggered by aggressive write-traffic, not read).
- Marginal value of the remaining 20% (upload/schedule):
  - **Real if** AI Coach is the primary plan author: Coach builds .zwo + season event → user wants it on the watch face for tomorrow's ride. Without push, the user copies the workout manually.
  - **Marginal if** the user is a watch-first author: most athletes still build/schedule workouts in Garmin's UI on the watch or phone.

**Finding A0.3-001 (Blocking-ish):** Even though the user chose Bidirectional, the *risk-adjusted MVP* is download-only. Recommend staging the build: Phase-1 ship = download only; Phase-2 ship = workout upload; Phase-3 ship = schedule push. Each phase has its own DEC-011 rollout gate. This protects against Garmin breaking the SSO flow mid-build (cheaper to walk away from a download-only feature than a full bidirectional one).

→ Surface to user for disposition.

## A0.4 Do-nothing analysis

Cost of inaction (per-user, per-year):
- Strava round-trip users: lose structured-workout data, lose HRV/readiness, accept a Strava dependency. Annoyance, not blocker.
- Linux smart-trainer users: **no path** to get activities into GC without manual FIT export. Migration risk → competitor (Intervals.icu/TrainingPeaks).
- Users who pay Garmin Connect+ for advanced metrics: the metrics never reach GC. Pay-for-feature, don't-use-feature.

Cost of building (rough order of magnitude):
- ~2-4 person-weeks for Phase-1 download-only.
- Ongoing maintenance: ~1 day per Garmin SSO change (historically ~1-2 times/year).
- Ongoing distribution: one extra pip wheel (`garminconnect`, `curl_cffi`) in installers — non-trivial on Windows.
- ToS risk: account suspension for the user. Mitigation: aggressive default rate limits, first-connect warning.

**Finding A0.4-001:** Cost of inaction is meaningful only for Linux + smart-trainer + structured-data users. That subset is small in absolute terms but it's *exactly* GoldenCheetah's most-engaged demographic (open-source, power users). Build is justified.

## Disposition (to be confirmed by user)

Proceed to DEC-001 with **Bidirectional** as the *strategic* scope, but with the **risk-adjusted recommendation** that Phase 1 ships activity-download-only. Upload + schedule push become Phase-2/Phase-3 DECs with their own gates. This is reflected in the cascade-impact column of DEC-001 alternatives.
